# 規劃：需求、UX、切片

> 何時讀：預製期寫需求、做 UI/UX、拆 Story／Task 時。

## 需求清單
目標使用者、核心情境、功能清單、非功能需求（目標平台、可用性、效能預算、讀寫比例、併發情境、敏感資料、日誌與監控、安全）、範圍外項目、里程碑、待使用者決定的問題。

## UX：以市面產品為參考，避免過度設計
- 設計前先找 2–3 個同類成熟產品，列出名稱、參考的畫面或流程、沿用了哪些慣例。
- 優先沿用使用者熟悉的版面、元件與操作，不自創互動。
- 只做需求清單裡有的功能和狀態；沒有需求支撐的畫面、動畫、設定項一律不做。
- 偏離參考慣例要寫明對應哪條需求，寫不出就照慣例。
- 每個畫面要有空、載入、錯誤、降級狀態；用 HTML 原型或 Figma。

## Task 工單內容
ID、標題、所屬 Epic/Story、所屬層級、`scenarioIds`、測試清單與路徑、**允許修改的檔案範圍**、相依工單、完成定義。寫到中低階模型不用猜就能實作；盡量一張只動一層。

## 切片規則：一輪做完、TDD 交付、不留半成品
- 垂直切片：每張 Task 交付一個可觀察行為，TDD 案例能在**一輪（一個代理工作階段）**內全轉 GREEN（D12）。
- 大小上限（參考）：BDD 情境 1–3 個、修改檔案約 5 個、最多跨 2 層、一個代理的上下文放得下。超過就再切。
- 每張可獨立合併，不依賴未完成工單；不開「第 1/N 部分」這種合併後留半成品的工單。
- Feature flag 只在無法再切時用，寫明理由與移除時機。

## 發布規劃
每個 Feature／Epic 寫預計版本、要不要 Feature Flag、發布策略、健康指標與回滾方式，並建 Planned 狀態的 Deployment 卡（先 Staging RC 再 Prod）。細節見 `release-deploy.md`。
