# 測試策略、資料一致性、可觀測性

> 何時讀：訂測試層級與覆蓋率、處理交易／併發／寫檔、設計日誌與錯誤處理時。

## 測試策略
- **單元**：領域層與 Use Case，用假 Port 隔離 DB、檔案、平台。核心業務覆蓋率 ≥ 80%，領域層目標接近 100%。
- **整合**：每個 Adapter 對真實依賴至少一組，在各目標平台跑。
- **E2E**：從渲染層操作到資料落地的主要流程，對應 BDD，是介面實測的基礎。
- TDD 分工與節奏見 `bdd-tdd.md`。

## 資料一致性與併發
- **交易在應用層開**：一個 Use Case 的多個寫入全成或全敗；領域層不知道交易存在，經 Port（Unit of Work）控制。
- **併發控制**：讀多寫少用樂觀鎖（版本號），高衝突寫入用悲觀鎖。桌面 App 也要考慮多視窗、多執行緒、背景任務同時寫入，寫明用哪種鎖。
- **跨系統**：真的跨多個資料庫或服務才用 Saga（含補償）；避免 2PC。
- **可恢復寫入**：寫檔用暫存檔＋原子替換；重試的操作要冪等。

## 可觀測性
- **結構化日誌**：不用 `print`／`console.log`／`Write-Host` 當日誌；用日誌套件（Rust `tracing` 等）輸出結構化格式與等級。日誌是輸出 Port，領域層不直接寫。
- **Trace ID**：每個請求或操作在 API 層產生，貫穿各層日誌。
- **全域例外處理**：API 層統一攔截，記日誌後回友善安全訊息；絕不暴露 DB 錯誤、內部路徑、stack trace。
- **監控**：有服務端時監控 CPU、記憶體、回應時間、錯誤率並告警；桌面 App 至少要本機日誌、崩潰報告、健康檢查。

## 各層對照
| 層 | 上線議題 |
|---|---|
| 渲染 | 防 XSS、輸入提示、友善錯誤畫面 |
| API | 認證授權、輸入驗證、全域例外、Trace ID、結構化日誌 |
| 應用 | 交易、併發鎖、Saga（必要時）、冪等重試 |
| 領域 | 純商業規則、充血模型、近 100% 單元測試 |
| 基礎設施 | 參數化查詢、安全儲存、日誌遮罩、整合測試 |
| 跨層 | 效能預算、複雜度上限、benchmark 回歸（`performance-memory.md`） |
