# 寫法：SOLID、Clean Code、自我審查清單

> 何時讀：實作期寫程式、提交前自我審查、審查者檢查寫法與註解時。

## SOLID，但不過度設計
- **S** 一個類別或函式只有一個改變的理由。**O** 新增行為優先擴充，不改穩定程式。**L** Adapter 必須能完全替換其介面。**I** 介面小而專一。**D** 高層依賴抽象（Port）。
- **不過度設計**：只為工單和 BDD 實際需要的情境寫抽象。只有一種實作就不做工廠、策略或泛型框架；三次重複才抽共用。
- SOLID 與簡單衝突時，以工單範圍與可測試性為準；拿不定選簡單的，回報裡寫一句理由。

## Clean Code
1. **命名名副其實**：揭示意圖（`elapsed_days` 不是 `d`），不誤導，可搜尋；除短迴圈計數器外不用 `e`、`data`、`tmp`。
2. **函式短小專一**：盡量 20 行（上限 30）；參數 0–2 個，3 個以上封裝成物件。
3. **用程式表達而非註解**：只留解釋「為什麼」、業務規則、非直覺取捨、後果警告、複雜度理由的註解；要白話、讓不熟的人讀一次就懂。刪掉重述程式的註解、過時註解、被註解掉的程式、沒工單號的 TODO、日誌式修改紀錄。
4. **錯誤處理不破壞邏輯**：不回傳 `-1`／`"ERROR"`，用明確錯誤型別（Rust `Result<T, 專屬 enum>` + `?`，產品程式不用 `unwrap()`/`panic!` 處理可預期錯誤；TS 自訂 Error；Python 領域例外，不用 `ValueError`）。錯誤在 API 層統一轉成對外格式。
5. **不傳入也不回傳 null**：空集合、`Option`、`T | undefined` + `?.`。
6. **童子軍法則**：只限工單允許的檔案、你本來就在改的程式附近，不改行為；範圍外問題寫進回報。

## 把架構落實到程式
1. **衛句**：不合法條件一開頭就 return／回錯誤，核心邏輯不縮排。
2. **依賴注入**：服務經建構函式接收 Port，組裝只在 composition root 做一次，測試注入假實作。
3. **充血模型**：領域物件自己管狀態與規則（`member.deduct_points(n)`），屬性不外露。單純 DTO／設定物件不必硬加行為。
4. **宣告式**：資料轉換優先用 `filter`/`map`/`collect`；鏈太長、有副作用或熱路徑時用清楚的迴圈。
5. **消除魔法數字**：enum、具名常數、以行為命名的方法（`user.lock_account()`）。

## 提交前自我審查清單
- 工單範圍內沒有 TODO 樁、半成品、被 skip 的測試；TDD 全部 GREEN。
- 函式 ≤ 30 行（目標 20）、參數 ≤ 3、巢狀 ≤ 2 層。
- 命名見名知意；沒有魔法數字、廢話註解、被註解掉的程式。
- 沒有錯誤碼、null、可預期錯誤的 `unwrap()`/`panic!`。
- 沒有意外修改全域或外部狀態；副作用集中在 Adapter。
- 沒有在方法內自行 new 依賴；領域物件不是只有 get/set。
- linter（`cargo clippy`、ESLint、PSScriptAnalyzer、ruff 等）沒有新增警告。
- 熱點路徑寫出複雜度推導；效能修改附前後量測（見 `performance-memory.md`）。

## 回答驗證者「為什麼這樣寫」
在工單備註或 PR 留言回答具體理由（需求、限制、量測數據、取捨），不可只說「比較好」。理由成立就補一行白話註解或測試；答不出就改寫成更直白的做法。不可因被提問擴大修改範圍。
