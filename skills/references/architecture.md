# 架構：原則、選型、分層

> 何時讀：預製期建架構骨架、實作時不確定程式該放哪一層、審查分層時。
> 適用範圍（D18）：GuGuBoard 管理的產品專案。DCC 工具專案的 Prototype 階段依全域 Stage 規則（先不抽象），驗證通過後才拆 Port/Adapter。

## 原則：跨平台高可用，非必要絕對不耦合
- **跨平台優先**：核心邏輯不依賴平台。作業系統、檔案、路徑、行程、外部 CLI、資料庫、雲端服務都經 Port 存取，各平台各自實作 Adapter。
- **高可用**：外部依賴失效時可降級或替換；設計逾時、重試、容錯與可恢復狀態。
- **非必要不耦合**：模組只透過契約溝通，不共用內部狀態。每個耦合都要寫「為什麼必要」，寫不出就拆開。
- 每個模組都能獨立測試、獨立替換。

## 選型
| 架構 | 依賴核心 | 優勢 | 代價 | 適用 |
|---|---|---|---|---|
| 傳統三層 | 資料庫 | 簡單、開發快 | 業務與 DB/ORM 耦合 | 簡單 CRUD |
| 洋蔥 | 領域層 | 業務核心純粹 | 介面與 DTO 轉換多 | 業務複雜、生命週期長 |
| 六角形 / Ports & Adapters | Port 介面 | 易換外部元件、多入口、易 Mock | 概念抽象 | 多入口、多儲存、跨平台 |
| CQRS | 命令端／查詢端分開 | 讀寫各自最佳化 | 最終一致性延遲 | 讀寫比懸殊、寫入極複雜 |

- **預設六角形 + 洋蔥**：領域在最內層，經輸入埠被呼叫、經輸出埠（Repository、檔案、外部服務、平台 API）呼叫外部。
- 三層只用在明確簡單 CRUD 且寫明理由；業務規則仍不得直接寫 SQL 或依賴 ORM 型別。
- CQRS 只在有明確讀寫差異時加，寫明一致性策略；否則只用命令層封裝寫入意圖。
- 架構文件寫出：選了哪種、為什麼、捨棄了哪些、未來在什麼條件下升級。

## 五層與職責
| 層 | 職責 | 常見元件 |
|---|---|---|
| 1 渲染 | 把資料轉成畫面，不放業務邏輯 | HTML/CSS、React/Vue、View 模板 |
| 2 API（輸入 Adapter） | 路由、狀態碼、認證、參數校驗、DTO 轉換 | Controller、REST、gRPC、Tauri command |
| 3 命令 | 把狀態變更封裝成 Command | `SubmitOrderCommand`、Handler |
| 4 應用 / Use Case | 編排流程、管交易、經 Port 協調基礎設施；不含商業規則 | Application Service |
| 5 領域 | 純商業規則，零框架／DB／UI／平台依賴 | Entity、Value Object、Domain Service、Domain Error |

**依賴方向**：渲染 → API → 命令 → 應用 → 領域，只能由外往內。
- Port 由內層定義，Adapter 放基礎設施，應用層經 Port 呼叫（依賴反轉）。
- 不跳層：渲染層不碰應用層或 DB；API 層不寫商業規則；應用層不寫計算規則。
- 層間只傳 DTO／Command／領域物件，不外漏內部型別（ORM 實體不得回到 API）。
- 目錄結構要能看出分層。

**標準資料流（提交訂單）**：渲染層按「結帳」→ API `POST /api/v1/orders` 驗權限與參數 → 包成 `SubmitOrderCommand` → 應用層開交易、經 Port 讀會員與購物車 → 領域算折扣、檢庫存、扣點數 → 應用層經 Port 儲存 → API 回 JSON → 渲染層更新。
